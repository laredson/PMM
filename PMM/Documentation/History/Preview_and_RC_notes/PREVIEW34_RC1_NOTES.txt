PalModMerger v1-preview34-RC1
=============================

Release-candidate focus
-----------------------
RC34 freezes the runtime-proven preview33 merge behavior and hardens the product
around it. PMMCore remains 0.8.1 and the production adapters/mappings are not
changed by this release candidate.

Runtime baseline entering RC34
------------------------------
Confirmed in Palworld on 2026-08-16:
- MultiJump Double / Triple / Quad can be active simultaneously and PMM exposes
  one value-level jump-count decision.
- The selected jump variant works together with FlyMode.
- FlyMode + WingPackNoWingCells_VisibleOnlyWhileFlying works through
  ContainedDeltaSuperset-v1; wing mesh visibility during Fly/glider flight is
  runtime-proven for the captured hashes.
- Stack/ZeroWeight, FoodNeverSpoils, EarlyAquaticConstructionKit and the existing
  BreedFarm / PlayerStatus compatibility families continued to work in the tested
  combined overlay.
- RushoarBoneToLeather_P.pak also works alongside the full tested set. It does
  not currently collide with another active provider in the captured fixture,
  but its fixed-size DataTable edit is recorded in Knowledge as a future merge
  regression/semantic example.

New in RC34
-----------
1. Saved compatibility patch library
   - Builds/Current AND Builds/Previous are visible in the UI.
   - Deployed PMM overlays are also represented and locally backed up.
   - A radio-button selects exactly one saved patch for Deploy.
   - Only patches whose exact active source hashes and mappings match are
     selectable.
   - Different previous true-conflict decisions from the SAME exact source set
     remain valid rollback choices. This supports switching between previously
     built Double / Triple / Quad overlays without rebuilding.
   - Deployment suppressions come from the selected patch manifest, so rollback
     restores the source-alternative policy that belongs to that patch.
   - After successful Deploy, the selected patch is promoted to Builds/Current
     and the previous Current patch is archived under Builds/Previous.

2. Knowledge Library promoted to a product feature
   - Settings shows bundled behavior/fixture/runtime-proven counts.
   - Knowledge remains explanatory/regression input only; it never bypasses the
     proof requirements of a production adapter.
   - Runtime-proven MultiJump N-provider, Fly+Wing and Rushoar Bone->Leather
     evidence is carried forward.

3. Community AI / modder handoff
   - Unsupported cases continue to generate one self-contained
     AI_HANDOFF_<caseId>.zip.
   - The ZIP now also carries sanitized global source-set/plan context and the
     community contribution workflow document.
   - Users can send that ZIP as-is to an AI or modder and return one
     PMM_MANUAL_SOLUTION_V1 solution ZIP.
   - PMM validates case identity, hashes, path safety, topology and AssetReader
     readability before accepting a solution as experimental/runtime-unproven.
   - Successful runtime results can be contributed with the original handoff and
     returned solution so future PMM releases can generalize the structural
     lesson into Knowledge/adapters instead of hard-coding mod filenames.

Release-candidate acceptance
----------------------------
The intended final gate before v1.0 is:
1. Analyze the proven active fixture with Double+Triple+Quad+Fly+Wing and the
   existing stack.
   Expected: Shared 6 | Auto merged 4 | Decisions 1 | Unsupported 0 |
             Experimental 0 | Identical 1
2. Build at least two different jump choices without deleting the earlier patch.
3. Confirm the patch panel lists Current + archived variants and only same-source
   variants are selectable.
4. Select an older variant and Deploy without rebuilding. Confirm the game uses
   that jump choice while Fly+Wing and the rest of the stack remain functional.
5. Select the newer variant and Deploy it back.
6. Disable/add a source mod and Analyze. Patches from the old source set must
   become non-selectable.
7. Optionally validate HAND TO AI / MODDER on a deliberately unsupported case.

If these gates pass, the recommended next step is v1.0 with the merge core
frozen and future compatibility growth delivered through new fixtures,
Knowledge updates and proven adapters.
